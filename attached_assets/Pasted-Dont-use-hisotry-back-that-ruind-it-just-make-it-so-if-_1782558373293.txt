The bug — a race condition in cloud sync

When you move a manga to a new category, the app fires two background pushes to the cloud in quick succession:

First push: manga with categoryIds: ['default'] (fired when the manga was first added to the library)
Second push: manga with categoryIds: ['your-new-category'] (fired when you moved it)
Both pushes have the same addedAt timestamp (set once at the moment you first saved it). The cloud merge logic was incoming.addedAt >= stored.addedAt — equal timestamps meant whichever network request arrived last won. If the first push happened to land after the second one (a very normal occurrence on a slow connection), it would silently overwrite the correct category assignment back to ['default']. By the time the PWA synced, it was pulling the already-corrupted cloud state.

The fix — three changes

storage.ts — Added an optional updatedAt field to SavedManga. Every mutation that changes a library entry now stamps updatedAt: Date.now():

addToLibrary — stamps on first save
setMangaCategories — stamps when you move manga between categories
batchPatchLibrary — stamps when bulk re-categorizing from library selection
library.ts (backend) — Changed the merge comparison from addedAt >= addedAt to max(addedAt, updatedAt) >= max(addedAt, updatedAt). Now the push that carries the category change (which has a higher updatedAt) always beats an older push of the same entry, regardless of network arrival order.

The updatedAt field is optional and backward-compatible — existing library entries without it fall back to addedAt, so nothing breaks for data already in the cloud.
